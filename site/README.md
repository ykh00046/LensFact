# LensFact Real-Data Pilot

This directory contains a no-build static pilot for LensFact using verified public data for nineteen transparent spherical contact-lens products distributed in Korea.

## Structure

This directory is the web root. Every internal link is relative, so the site works from any root path.

The header nav is the same six links on all 50 pages, in both the desktop and the mobile copy: 포장 숫자 해석 (`decoder/index.html`), 제품, 검색, 공식 사양 비교, 렌즈 상식, 소개. Each page whose section has a nav entry marks it with `aria-current="page"` — two copies, desktop and mobile; the policy pages carry one, because they appear in the mobile nav only. The home page and the ten `terms/` pages mark none: home because the brand anchor — not a nav item — is the link home, the terms pages because the nav has no 용어 entry. Below 900px the desktop nav is hidden and the menu button needs JavaScript, so every page's `<head>` also carries a `<noscript><style>` block that hides the dead toggle and lays the mobile nav out in flow.

The home page is a router with a ledger above it: a hero and the 검증 원장 panel state what the catalogue is and how much of it is confirmed, and an ordered index of three route rows sends the reader to one of the three things the site does. Three reading flows then tie the pages together. A reader holding a package opens `decoder/index.html` from the first route row, types the figures printed on the blister and reads each figure's meaning plus the products that print the same value. A reader who searched for one word instead lands on `terms/<field>.html`, reads what the figure means, and follows a value row into `products/index.html?<field>=<value>`, which shows only the products printing that value and lists the condition as a removable chip. A reader who came for one product searches from the home page's second route row or the header's 검색 link into `products/index.html#product-search`, opens `products/<slug>.html`, and reads each value with its source. From that product page the 이 제품과 비교하기 button opens `compare/index.html?p=<slug>` with the product as the first column, more products are added in the picker, and every row header in the table leads back to the term page for that figure. A reader who searched for one product against another lands on `compare/<id-a>-vs-<id-b>.html` instead: a static page for that one pair, which sorts the two products’ official figures into what can and cannot be placed in the same table, links back into the tool with both products preselected, and sends the reader on to either product page.

- `index.html`: home page — a router and the evidence ledger, and nothing else. A hero (h1 + one lead sentence carrying `[data-product-count]`, filled from `products.js` at runtime so it cannot drift from the data) beside the `[data-evidence-summary]` 검증 원장 panel, then an ordered route index of three rows — 포장 숫자 해석 -> `decoder/index.html`, 제품 찾기 -> `products/index.html#product-search`, 제품 비교 -> `compare/index.html`. Each row is a static link whose title is an `<h3>`, never a button, so screen-reader heading navigation reaches all three routes; the page runs h1 -> section h2 -> route h3. Below the routes sits one trust sentence marked `[data-evidence-summary]`, so its 미확인 count is refreshed from `products.js` and its static fallback is checked against the computed value in the tests; it keeps the 최종 피팅은 전문가에게 확인하세요 clause. Nothing else is above the shared footer: the spec-input form moved to `decoder/index.html`, the twenty-button preset decoder was removed outright, and the three evidence example cards moved to `products/index.html`. An inline `WebSite` JSON-LD block carries the site name and description; it declares no `SearchAction`, because the product search has no results URL scheme to point at.
- `decoder/index.html`: the 포장 숫자 해석 page. It carries the `#input-decoder` form (BC, DIA, 함수율, Dk/t, 재질명, 교체주기 — all optional, at least one required): the reader types the figures printed on their own package and gets each figure's meaning plus a factual placement statement against `products.js` and a `표기 일치` product list. Values are computed in the page only: nothing is stored and nothing is sent. Every control and the result panel ship `disabled` / `hidden` and are enabled by `initInputDecoder()`, so with JavaScript off no reader can press a button that would only reload the page and discard what they typed. The form declares `data-product-base="../products/"` so the match links resolve from this depth; the attribute defaults to `./products/` when absent. `INPUT_FIELDS` covers six of the nine fields, so a visible 표기 뜻 전체 보기 block links all nine `terms/<field>.html` pages and marks the three that have no input box, and a `<noscript>` block states that the form needs JavaScript and repeats those links plus `products/index.html`.
- `products/index.html`: under the hero and above the grid sits the three-card `[data-evidence-examples]` section (moved off the home page on 2026-08-29; the attribute is the anchor `tests/static-content.test.js` locates it by), which shows three products whose official sources disagree and links each to its `./<slug>.html` page. The list itself is nineteen static product cards written into the page markup; `initProductIndex()` reads those cards and only shows and hides them — it renders none of them from `products.js`. Besides the search box and the 제조사/교체주기 selects, the list accepts spec deep links `?bc= ?dia= ?water= ?dkt= ?material= ?replacement=` (exact value match through the shared parser: a conflicted field matches either recorded value, an unknown field never matches) and `?q=` to prefill the search. Active spec conditions appear as removable chips above the grid and are mirrored in `history.replaceState`. The header's 검색 link and the home page's second route row both point at `#product-search`. That id sits on the list `<section>`, not on the search input, because the filter wrapper ships `hidden` and a `display: none` element cannot be scrolled to; a reader without JavaScript therefore still lands on the product list, and with JavaScript `initProductIndex()` moves focus into the search box once the controls are enabled.
- `products/<slug>.html`: one page per product (`acuvue-oasys-1-day`, `dailies-total1`, `biofinity`, `acuvue-moist-1-day`, `myday`, `clariti-1-day`, `acuvue-oasys-2-week`, `precision1`, `biotrue-oneday`, `acuvue-oasys-max-1-day`, `dailies-aquacomfort-plus`, `acuvue-vita`, `total30`, `airoptix-plus-hydraglyde`, `proclear-1-day`, `biofinity-energys`, `ultra-one-day`, `miru-1day`, `soflens-daily`). Thin HTML shell plus `<main data-product-page="<id>">`; `initProductPage()` renders every field with its full source list open, and a `<noscript>` table carries all values and the first source per field for crawlers and no-JS readers. Each page's comparison card carries a 이 제품과 비교하기 button linking `compare/index.html?p=<slug>`, which opens the comparison with that product as its only column.
- `knowledge/index.html`: content hub over the nine topics in `articles.js` — three completed articles, four topics a `terms/<field>.html` page already answers (BC, DIA, 허가번호, UV) rendered as linked cards, and two still marked 준비 중.
- `knowledge/water-content-moisture.html`: evidence-based article about water content and perceived moisture.
- `knowledge/contact-lens-bc-dia-pwr.html`: official-source guide to reading PWR, BC, and DIA without treating the three axes as a quality score.
- `knowledge/contact-lens-dk-dkt.html`: official-source guide to separating material Dk from thickness-dependent Dk/t and checking units, method, temperature, correction, power, and thickness before comparison.
- `terms/index.html`: list of the nine field terms under an `<h2>`, rendered from `fields.js` with each term's value count. The heading is not decoration: the cards are `<h3>`, so without it the page ran h1 -> h3.
- `terms/<field>.html`: one page per field (`bc`, `dia`, `water`, `material`, `dkt`, `thickness`, `replacement`, `permit`, `uv`). Thin HTML shell plus `<main data-term-page="<id>">`; `initTermPage()` renders the meaning and caution from `fields.js` and a value-distribution table from `products.js` — one row per printed value with the products printing it, conflicted products appearing under each of their recorded values with their full printed string, and unknown ones grouped as 확인되지 않음. Rows for the six deep-linkable fields carry a `이 값으로 목록 보기` link into `products/index.html?<field>=<value>`. The `permit` page explains the 수허/제허 prefixes and MFDS lookup, the `uv` page separates 등급 표기, 차단율 and 투과율. A `<noscript>` copy of the same table is generated from the same `app.js` function, so the two cannot drift.
- `compare/index.html`: accessible official-spec comparison rendered from `assets/data/products.js`. A checkbox picker (`fieldset` "비교할 제품 선택") chooses up to 4 products (default: the first 3); the selection persists in the URL query `?p=<id>,<id>` so a comparison is linkable (a single id arriving from a product page renders one column and the picker hint asks for more), every row header links to that field's `terms/<field>.html` page in both the live and the `<noscript>` table, and `<noscript>` keeps the full all-product table and evidence list.
- `compare/<id-a>-vs-<id-b>.html`: one static page per recorded product pair (`acuvue-oasys-1-day-vs-dailies-total1.html`, `acuvue-oasys-1-day-vs-acuvue-moist-1-day.html`, `myday-vs-clariti-1-day.html`, `dailies-total1-vs-dailies-aquacomfort-plus.html`, `biofinity-vs-airoptix-plus-hydraglyde.html`, `acuvue-oasys-1-day-vs-acuvue-oasys-max-1-day.html`, `acuvue-oasys-1-day-vs-acuvue-oasys-2-week.html`, `dailies-total1-vs-total30.html`). Thin HTML shell plus `<main data-compare-pair="<id-a>,<id-b>">`; `initComparePairPage()` renders the whole body from `products.js` through `pairBodyMarkup()`, and the committed `<noscript>` copy is the output of the same function with the `ns-` id prefix. The file is generated by `tools/build-pair-pages.js` — run it after any product data change and never hand-edit a pair page; `tests/static-content.test.js` fails when a committed file differs from the generator. The pages answer which of the two products' official figures can be placed in one table and which cannot, with the reason derived from that pair's own states, conflicts and printed measurement conditions; they carry no recommendation, ranking or score. The pair order in a file name follows `COMPARE_COLUMNS`, so one pair has exactly one URL. Each page links into `compare/index.html?p=<id-a>,<id-b>`, into both product pages, and into the other pair pages its two products appear in; `compare/index.html` lists every pair page and, when the picker selection equals a pair, points at that page through `[data-compare-pair-link]`.
- `about/index.html`: what the site does and does not do, its independence statement, and contact.
- `policy/editorial.html`: editorial policy, evidence states, medical boundary, correction procedure.
- `policy/methodology.html`: source hierarchy, meaning of `raw`/`condition`/`verifiedAt`, why values are not merged.
- `policy/privacy.html`: privacy policy for the current no-cookie, no-analytics, no-ads site.
- `404.html`: the error page GitHub Pages serves for every unmatched path under the site. Same header, footer and boundary sentence as every other page, in Korean, with the three home routes and the product and term indexes; it is the only page with no `<h1>`-bearing content of its own to offer, so it offers the way back instead. Two things make it unlike the rest: it carries **no `<link rel="canonical">`** and no `DOMAIN-TBD` — an error page must not tell a crawler it is the real address of something — and it is deliberately **absent from `sitemap.xml`**, which `tests/static-content.test.js` enforces through a named exemption rather than a filter. It also loads `assets/js/app.js` alone, without the two data files, because it renders no product value and so has no count that could go stale. Pages is serving this file for a URL that is not its own, so the browser resolves its relative links against the *requested* directory: at `/products/typo.html` the stylesheet would be looked for under `/products/assets/`. An inline script in the head recovers the site root — the site's top-level directories are a closed set, so the last path segment naming one of them sits one level below the root — inserts a `<base>` for the body's links, and `document.write`s the two stylesheet links and the `app.js` tag with that root already prefixed. The writing is the point: a `<base>` cannot win a race it starts too late, because Chromium's preload scanner resolves any `href` in static markup against the document URL before the parser reaches the script, so a literal `./assets/...` link would be speculatively fetched from `/products/assets/` and 404 before the base existed. No literal relative subresource URL is left outside the `<noscript>` block, which carries the same two stylesheets so the no-JS rendering is unchanged. The test reads the directory list back off `site/`, so it cannot drift from the file tree, and fails if a subresource URL reappears in the static markup.
- `robots.txt`, `sitemap.xml`: discovery files. Both still contain the `DOMAIN-TBD` placeholder origin. `robots.txt` is inert on the current preview: GitHub Pages serves this as a project site under a path prefix, so crawlers read the origin root's `robots.txt`, which this repository does not control. The indexing block that actually works during the preview is a per-page `<meta name="robots" content="noindex, nofollow">` on line 6 of every one of the 50 pages, directly under the `viewport` line; `tools/build-pair-pages.js` emits the same line so regenerated pair pages keep it, and `tests/static-content.test.js` fails if any page loses it. `sitemap.xml` lists 49 of the 50 — every page but `404.html` — each with a `<lastmod>`; the eight pair pages' `<lastmod>` must equal `PAGE_DATE` in `tools/build-pair-pages.js`, which is also their JSON-LD `dateModified`, and a test holds the two together.
- `assets/css/style.css`: shared responsive stylesheet.
- `assets/fonts/pretendard/`: self-hosted Pretendard Variable (SIL OFL 1.1). `pretendard-dynamic-subset.css` declares 92 `@font-face` rules for the family `Pretendard Variable`, each with its own `unicode-range` and `font-display: swap`, pointing at the woff2 slices in `woff2-dynamic-subset/`. Every page links this stylesheet immediately before `assets/css/style.css`. The browser downloads only the slices a page's characters actually need, so a Korean page fetches a few tens of KB rather than the whole 2.9 MB set. `LICENSE.txt` is the upstream OFL text.
- `assets/js/app.js`: vanilla JavaScript for the menu, the input decoder on `decoder/index.html`, source details, filters, the comparison table, the product list and product pages, the term pages, and disabled ad slots.
- `assets/data/products.js`: repository-owned verified product values, evidence states, and official source URLs, plus each product's `slug` and `aliases` (Korean sales name, English global name, material name, and the US sales name where it differs from the Korean one). This file is the site's whole product: `tests/provenance.test.js` holds the shape of every source record in it (non-empty `raw` original wording, a plain `https` url, a `YYYY-MM-DD` `verifiedAt` inside a bounded window, a state from the known enum, the same nine fields on every product) and rebuilds every `<noscript>` fallback on the site from these records. Beyond that, every leaf of the file — value, state, `raw`, `url`, `verifiedAt`, `condition`, `organization`, `document`, `linkNote` — is hashed into `tests/products.snapshot.json` by `tools/products-snapshot.js`, with one digest per product so a failure names the record that moved. The digest is the only guard that catches a rewritten `raw`: no page prints the original wording of every source, so no rendering test can see it change.
- `assets/data/fields.js`: common field terminology used across all products.
- `assets/data/articles.js`: content status and metadata. `status: "term"` marks a hub topic that a term page already answers (BC and DIA); it renders as a linked card instead of 준비 중.

## Run Locally

From this directory:

```bash
cd site && python -m http.server 4174
```

Open `http://localhost:4174/`.

## Deployment

`.github/workflows/deploy-pages.yml` publishes this directory to GitHub Pages on every push to `main`. The job runs `node --test "tests/*.test.js"` before it uploads the artifact, so a failing suite stops the run and the previously deployed version stays live. That gate is not ceremony: the suite is what holds the preview `noindex` meta on every page, `sitemap.xml` against the files on disk, the generated pair pages against `products.js`, and the committed provenance digest — the exact drift that would otherwise reach the public URL unnoticed.

## Data and Source Scope

The pilot covers ACUVUE OASYS 1-Day, DAILIES TOTAL1, Biofinity, 1-DAY ACUVUE MOIST, MyDay, clariti 1 day, ACUVUE OASYS 2-Week, PRECISION1, Biotrue ONEday, ACUVUE OASYS MAX 1-Day, DAILIES AquaComfort Plus, ACUVUE VITA, TOTAL30, AIR OPTIX plus HydraGlyde, Proclear 1 day, Biofinity Energys, Bausch + Lomb ULTRA ONE DAY (US name INFUSE One-Day), Miru 1day Menicon Flat Pack, and SofLens daily disposable transparent spherical products. Korean official product pages, Korean IFUs, CooperVision Korea's 2023 specification sheet, CooperVision's global product reference guide, Alcon's US and international professional specifications, Alcon's and Bausch + Lomb's package inserts and fitting guides, Menicon Korea's consumer and professional product pages with Menicon's English instructions for use, and the MFDS UDI lookup are used to identify Korean distribution and permit information. DAILIES AquaComfort Plus and AIR OPTIX plus HydraGlyde are the two products with no Korean official page at all; their Korean distribution is identified from the MFDS UDI ledger alone. Manufacturer technical or professional specifications supply BC, DIA, water-content, Dk/t, and thickness values. The comparison and summary permit row is labelled `한국 허가번호` with a `수허(수입)·제허(제조)` note because the prefix is part of the recorded value rather than something the table supplies; every product currently on file carries 수허. Scientific literature supports the water-content article.

Source links are ordinary user-initiated external links. The pages load no external scripts, styles, images, analytics, advertising, APIs, or CDNs at runtime; the web font is served from this site's own origin alongside the pages, never from a font CDN. `ADS_ENABLED=false` remains fixed and all ad-slot elements stay hidden.

## Remaining Limitations

- Permit display values follow the MFDS UDI ledger string; each manufacturer document keeps its own spelling verbatim in its `raw` record, so the same number can appear with and without a space or a trailing `호` depending on the source.
- Biofinity's official sources disagree on Dk/t (`170` versus `171 at -3.00D`) and UV (`기술 적용` versus `No` versus no UV row at all on the US practitioner page). All versions remain visible.
- Biofinity's and MyDay's centre thickness are `unknown`: no reviewed official source states the value. Dk/t depends on thickness, so both Dk/t figures are read without that condition.
- Two corrections were applied on 2026-08-28 and logged in `docs/verification/CORRECTIONS.md`: Biofinity's centre thickness `0.08 mm` was withdrawn for lack of a reproducible source, and CooperVision Korea's legal name was fixed from `쿠퍼비젼코리아(주)` to `쿠퍼비전코리아(주)`.
- A source-by-source audit of the three pilot products on 2026-08-28 (`docs/verification/audit-pilot-2026-08-28/`) replaced four unreproducible `raw` quotations (ACUVUE OASYS 1-Day material and replacement, Biofinity replacement, DAILIES TOTAL1 replacement), moved both outstanding permit records onto the MFDS UDI ledger (`수허 16-499 호` 497 records, `수허 08-131 호` 94 records — Biofinity's displayed value gained its `호`), corrected eight further `raw`/`document` strings to the printed originals, and re-dated every touched record to `2026-08-28`. All of it is logged in `docs/verification/CORRECTIONS.md`.
- DAILIES TOTAL1's core and surface water values use different locations and methods and are not combined into one number.
- Public specifications do not predict individual comfort, fitting, prescription, or wearing outcome. The pilot offers no recommendation, ranking, score, purchase link, or diagnosis.
- 1-DAY ACUVUE MOIST's BC, DIA, water content, Dk/t, centre thickness and UV figures come from the global ACUVUE technical specification guide; no Korean official source states them, and the Korean page's UV percentages are image-only, so the Korean wording stays unverified.
- MyDay's UV entry is a grade (`UV 차단 · Class 2`), not a blocking percentage, and the specification sheet does not define which standard the grade belongs to.
- clariti 1 day's material name disagrees between official sources: the global specifications and the MFDS model name say `somofilcon A`, CooperVision Korea's 2023 sheet prints `stenfilcon A`. No correction notice was found, so both values stay visible.
